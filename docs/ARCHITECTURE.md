# Архитектура

Документ описывает устройство приложения: разделение расчётов и интерфейса,
поток данных, формулы и решения по представлению.

## Компоненты

| Модуль | Ответственность |
|---|---|
| `mortgage.py` | Ядро: формулы платежей, построение помесячного графика, годовая агрегация, сравнение схем. Не знает про Streamlit. |
| `app.py` | Представление: панель параметров, вкладки, графики Plotly, таблицы, выгрузка CSV. |
| `test_mortgage.py` | Smoke-тесты ядра против эталонных расчётов. |

Разделение намеренное: ядро — чистые функции и `dataclass`, интерфейс —
только показ. Ядро переиспользуется в тестах, консольных сценариях и любом
другом фреймворке без изменений.

## Поток данных

```
st.sidebar
   price, down, years, rate, method, income
        │
        ▼
principal = price − down
        │
        ▼
build_schedule(principal, rate, years·12, method)  →  MortgageResult
        │                                              │
        │                                              ├─ monthly_payment / last_payment
        │                                              ├─ total_paid / total_interest
        │                                              ├─ payoff_date, overpay_share
        │                                              ▼
        │                              st.metric × 6  (KPI-карточки)
        ▼
   schedule (DataFrame: №, Дата, Платёж, Основной долг, Проценты, Остаток долга)
        │
        ├── donut_figure()      структура выплат (тело vs проценты)
        ├── yearly_bar_figure() платежи по годам из yearly_summary()
        ├── balance_figure()    остаток долга + накопленные проценты
        ├── heatmap_figure()    доля тела долга: годы × месяцы
        ├── sankey_figure()     взнос + кредит → жильё, проценты → банк
        │
        └── st.dataframe + st.download_button (CSV)
```

Streamlit перезапускает весь скрипт на каждое взаимодействие, поэтому состояние
не хранится нигде: каждый пересчёт — полный проход по 240 месяцам
(миллисекунды), что избавляет от инвалидации кэша и рассинхронизации
графиков.

## Ядро расчётов (`mortgage.py`)

### Формулы

- **Аннуитет:** `r = rate / 12 / 100`; `платёж = P · r · q / (q − 1)`,
  где `q = (1 + r)^n`. При нулевой ставке — `P / n` (частный случай
  покрыт тестом).
- **Дифференцированный:** тело долга делится на равные части `P / n`,
  проценты начисляются на остаток, поэтому платёж убывает от месяца к месяцу.
- **Последний платёж** закрывает остаток целиком (`principal_part = balance`),
  чтобы накопленная погрешность округлений не оставляла «хвост» в копейках.
  Инвариант проверяется тестом: сумма тела долга = кредиту, финальный
  баланс = 0.

### Результат

`MortgageResult` (dataclass) — единый контракт между ядром и UI:

- `schedule: pd.DataFrame` — 6 колонок, одна строка = один месяц;
- `monthly_payment` (аннуитет — постоянный, дифференцированный — первый),
  `last_payment`, `total_paid`, `total_interest`;
- вычисляемые свойства `payoff_date` (дата закрытия) и `overpay_share`
  (доля процентов в выплатах).

### Агрегация и сравнение

- `yearly_summary()` сворачивает помесячный график в годовые итоги
  (платежи, тело, проценты, остаток на конец года, число месяцев в году) —
  она питает и столбчатую диаграмму, и «итоги по годам» в таблице.
- `compare_schemes()` считает обе схемы на одинаковых параметрах; вкладка
  сравнения показывает динамику платежей и разницу переплаты
  (на демо-данных дифференцированная схема дешевле на ~4,88 млн ₽).

## Представление (`app.py`)

### Вкладки

`st.tabs("Дашборд", "График платежей", "Сравнение схем")` — одна страница,
три раздела. Все графики строятся заново при изменении любого параметра.

### Графики

| Фигура | Что показывает | Почему выбрана |
|---|---|---|
| Donut | тело долга vs проценты | мгновенный ответ «сколько стоит кредит» |
| Bar по годам | платежи с разбивкой тело/проценты | видна фронтальная нагрузка процентами в первые годы |
| Line | остаток долга, накопленные проценты, погашенный долг | «когда переплата обгонит тело» |
| Heatmap | доля тела долга в каждом платеже | единственный способ увидеть структуру 240 платежей целиком |
| Sankey | движение денег: взнос+кредит → жильё, проценты → банк | объясняет, кому уходит что |

### Русская локаль

Plotly по умолчанию форматирует оси в западном стиле. Собственные тикеры
`rub_ticks()` и форматтеры `money() / pct()` дают ₽, разряды через пробел
и русские подписи во всех осях и hover-подсказках.

### Оценка кредитной нагрузки

Ввод ежемесячного дохода включает KPI «платёж от дохода» с ориентиром
на банковскую норму ≤ 30–40%: клиент сразу видит, проходит ли параметры
по бюджету.

## Тесты (`test_mortgage.py`)

Запуск: `python test_mortgage.py` (без pytest — smoke-раннер с явными
`assert`).

| Проверка | Инвариант |
|---|---|
| Аннуитет | совпадение с эталонной формулой до копейки |
| Нулевая ставка | платёж = тело/срок |
| Целостность графика | Σ тела долга = кредиту; финальный баланс = 0; 240 строк на 20 лет; даты в ожидаемых годах |
| Дифференцированный | тело долга убывает равными шагами |
| Экономика схем | переплата по дифференцированной < аннуитетной |
| Агрегация | годовые итоги сходятся с помесячным графиком |

## Конфигурация и эксплуатация

Переменные окружения не требуются; настраиваются только стандартные
параметры Streamlit (`--server.port`, `--server.address` и т. п.).
Инструкция установки с чистого компьютера, Docker-шаблон, systemd-юнит
и регулярное обслуживание — в [docs/OPERATIONS.md](OPERATIONS.md).

## Точки расширения

- **Досрочное погашение** — добавить в `build_schedule()` параметр
  `extra_payments`; модель уже помесячная, остальное — аккуратное
  перенаправление «суммы» в тело или срок.
- **Страхование и комиссии** — расширить `MortgageResult` дополнительными
  потоками платежей; Sankey и donut подхватят их автоматически.
- **Несколько предложений банков** — `compare_schemes()` уже принимает
  произвольные наборы параметров.
- **Кэширование** — при росте вычислений обернуть построение графика
  в `@st.cache_data` (ключи — параметры кредита).
